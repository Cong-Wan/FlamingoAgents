# 用量统计界面候选方案

- Author: wilbur
- Version: 1.1
- Date: 2026-09-21
- Status: 已按方案首轮审核同步修订，待用户选择
- Scope: 界面信息架构与交互草案，不修改业务代码

## 1. 对需求的理解

本次不是在当前页面继续堆功能，而是统一统计口径后重做信息层级：

1. 用量统计页的所有数字只读取同一个权威账本，并由一次接口响应返回，不能再让顶部汇总读 `sessions.json`、图表和费用读 `usage.db`。
2. 页面顶部提供六个固定时间筛选：`今天`、`昨天`、`近7天`、`近1个月`、`本月`、`上月`。
3. 顶部四项汇总保持原有指标、顺序和内容区顶部位置：`Prompt Tokens`、`Cached Tokens`、`Completion Tokens`、`总费用`；数值随筛选区间变化。
4. 筛选后只展示区间内有已落账模型调用的 Provider；一个 Provider 一张卡，卡片纵向排列。
5. Provider 卡内按模型展示调用次数与用量，彻底移除会话明细表，不展示会话名、sessionId、会话当前模型或更新时间。
6. 汇总、Provider、模型、费用及可选趋势来自同一筛选窗口、同一数据库快照。

> “顶部四个汇总不动”在此理解为：位置、顺序、指标不改，但数值应用当前筛选。合法零价显示 `$0.0000`；价格未知显示 `—`，不能把未知伪装成零。

## 2. 三个方案共有的顶部结构

时间筛选放在页面标题栏右侧，使四个汇总卡仍是内容区第一组信息：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ 用量统计                  [今天][昨天][近7天][近1个月][本月][上月]          │
├──────────────────────────────────────────────────────────────────────────────┤
│ ┌ Prompt Tokens ┐ ┌ Cached Tokens ┐ ┌ Completion Tokens ┐ ┌ 总费用 ┐       │
│ │   1,284,920   │ │    972,810    │ │      42,306       │ │ $8.26  │       │
│ └───────────────┘ └───────────────┘ └───────────────────┘ └─────────┘       │
│ 2026-09-15 00:00 ～ 2026-09-21 08:55 · Asia/Shanghai · 已落账调用 128 次  │
└──────────────────────────────────────────────────────────────────────────────┘
```

共同交互约束：

- 建议默认选中 `近7天`。
- 快速切换时只允许最后一次选择更新页面，旧请求不得覆盖新筛选结果。
- 桌面端为六段式按钮；窄屏可横向滚动或收敛为单选下拉，六个语义不变。
- 切换时四张汇总卡和全部 Provider 卡整体加载、整体更新，不能混合两个时间范围的数据。
- 无记录时保留四卡（token 为 `0`；仅价格覆盖明确时费用为 `$0.0000`），下方显示“当前区间暂无已落账用量”。
- `Cached Tokens` 是 `Prompt Tokens` 子集；任何“总 token”只使用 `Prompt + Completion`。
- 三个方案都固定显示紧凑口径说明：**仅包含已落账且 Provider 返回合法 usage 的终态调用；进行中及无 usage 的调用不包含，迟到补账可能回填历史。**
- 若当前窗口含迁移旧账、不可验证记录或迁移时价格估算，三个方案都显示黄色质量提示；“费用完整”只表示价格覆盖完整，不表示 Provider 账单准确。

## 3. 方案 A：精确清单型

### 3.1 示意

```text
┌ Provider · subGPT ───────────────────────────────────────────────────────────┐
│ 89 次调用 · 892,406 tokens · $6.43                                          │
├─────────────────────┬────────┬────────────┬────────────┬────────────┬──────┤
│ 模型                │ 调用数 │ Prompt     │ Cached     │ Completion │ 费用 │
├─────────────────────┼────────┼────────────┼────────────┼────────────┼──────┤
│ gpt-6-astra         │ 62     │ 620,120    │ 501,008    │ 18,450     │$4.82 │
│ gpt-5.6-sol         │ 25     │ 241,013    │ 201,500    │ 10,776     │$1.50 │
│ another-model       │ 2      │ 2,047      │ 1,920      │ 0          │$0.11 │
└─────────────────────┴────────┴────────────┴────────────┴────────────┴──────┘

┌ Provider · glm ──────────────────────────────────────────────────────────────┐
│ 39 次调用 · 434,820 tokens · $1.83                                          │
│ ...                                                                          │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 特点

- Provider 头部展示 Provider 汇总，模型使用规整表格。
- 最适合精确核对每个模型的调用数、Prompt、Cached、Completion 和费用。
- 信息密度最高，实现和测试成本最低，不依赖图表组件。
- 模型多时仍容易扫描；移动端需要把模型行改为指标网格，否则横向表格拥挤。

### 3.3 适用取向

适合把页面当作“准确统计概览”，重视精确读数胜过视觉比例。

## 4. 方案 B：模型占比型（推荐）

### 4.1 示意

```text
┌ Provider · subGPT ───────────────────────────────────────────────────────────┐
│ 89 次调用 · 892,406 tokens   Prompt 863,180 · Cached 704,428 · Output 29,226│
│ 3 个模型                                                       费用 $6.43   │
├──────────────────────────────────────────────────────────────────────────────┤
│ gpt-6-astra · 62 次                                      638,570 · $4.8210 │
│ ███████████████████████████████████████████░░░░░░░░░░░░  71.6%              │
│ Prompt 620,120  ·  Cached 501,008  ·  Completion 18,450                     │
│                                                                              │
│ gpt-5.6-sol · 25 次                                      251,789 · $1.5020 │
│ █████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  28.2%              │
│ Prompt 241,013  ·  Cached 201,500  ·  Completion 10,776                     │
│                                                                              │
│ another-model · 2 次                                          2,047 · $0.1070│
│ ▏                                                             0.2%           │
│ Prompt 2,047  ·  Cached 1,920  ·  Completion 0                            │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 特点

- 每个模型保留调用数和精确 token，同时用横向条直观看出它在该 Provider 的 token 占比。
- 横向条使用 `Prompt + Completion`；Cached 只作 Prompt 子指标，绝不重复叠加。
- 比 A 更容易识别主要消耗模型，又不会像完整趋势图一样让卡片过高。
- 桌面和移动端都能自然纵向收缩，最符合“Provider 卡片竖向排列”。

### 4.3 适用取向

适合日常快速判断“哪个 Provider、哪个模型调用多、耗量大”，同时仍可读精确值。它在信息密度、视觉表达和实现复杂度间最均衡，因此推荐。

## 5. 方案 C：Provider 趋势型

### 5.1 示意

```text
┌ Provider · subGPT ───────────────────────────────────────────────────────────┐
│ 89 次调用 · 892,406 tokens · 3 个模型 · $6.43                               │
│                                                                              │
│ 240k ┤                 ╭──╮                                                  │
│ 160k ┤       ╭──╮   ╭──╯  ╰╮       ■ gpt-6-astra                           │
│  80k ┤  ╭────╯  ╰───╯      ╰──╮    ■ gpt-5.6-sol                           │
│    0 └──15──16──17──18──19──20──21  ■ another-model                         │
│                                                                              │
│ gpt-6-astra 62次/638,570 · gpt-5.6-sol 25次/251,789 · another 2次/2,047     │
└──────────────────────────────────────────────────────────────────────────────┘

┌ Provider · glm ──────────────────────────────────────────────────────────────┐
│ ...另一个独立趋势图...                                                       │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 特点

- 每个 Provider 卡内按时间桶展示模型堆叠趋势，最容易发现某天或某小时突增。
- 时间桶随筛选确定：今天/昨天按小时，其余范围按天。
- 精确 Prompt/Cached/Completion 主要通过悬浮提示或摘要读取，直接核对不如 A/B。
- Provider 多时页面很长；图表 tooltip、空桶、颜色和移动端维护成本最高。

### 5.3 适用取向

适合“排查什么时候突然耗量”是核心场景。若主要目标是按 Provider/模型看总量，B 更直接。

## 6. 对比与建议

| 维度 | 方案 A 精确清单型 | 方案 B 模型占比型 | 方案 C Provider 趋势型 |
|---|---:|---:|---:|
| 精确读数 | 最强 | 强 | 中 |
| 快速识别主要模型 | 中 | 最强 | 强 |
| 观察时间趋势 | 无 | 无 | 最强 |
| 多 Provider 页面长度 | 短 | 中 | 长 |
| 移动端适配 | 中 | 最好 | 中 |
| 实现与维护成本 | 最低 | 中 | 最高 |
| 推荐度 | 备选 | **推荐** | 特定场景备选 |

**推荐方案 B。** 它完整满足“顶部四汇总 + 六时间筛选 + Provider 纵向卡片 + 按模型调用展示 + 无会话明细”，且不需要保留当前全局组合图。偏财务式核对选 A；明确需要分析时间波动才选 C。

## 7. 实施前决策

为了避免只选界面、却暗中替用户决定统计口径，请从下面任选一种回复：

### 快速确认

- `B + 采用推荐口径`（推荐）

推荐口径是：整个官方系统范围；近1个月 = 含今天的近30个自然日；日历边界使用服务端系统 IANA 时区并显示；历史采用“现存日志准确优先”；费用按 USD 调用时价格估算。

### 自定义确认

1. 界面：`A` / `B` / `C`；
2. 范围：`仅 Web` / `整个官方系统（Web + CLI + SDK + askSubAgent + library）`；
3. 近1个月：`近30个自然日` / `当前时刻向前一个日历月`；
4. 时区：`服务端系统时区` / 指定 IANA 时区；
5. 旧历史：`现存日志准确优先` / `旧 DB 覆盖优先` / `升级时刻清零`；
6. 费用：`USD 调用时估算` / `不展示`（若不展示则需再次确认如何处理“顶部四项不动”中的费用卡）。

三种旧历史策略的取舍详见 `docs/plan/260921_usageStatisticsRepairPlan.md` §6；无法同时做到旧数据绝对完整、绝对准确和无重复，因此必须显式选择。
