# 代码审核报告 — @ 压缩包与其它文件提示不支持

## 总览

- 审核范围：8 个文件。`fileBrowser.py`、`fileMention.js`、`fileExplorer.js`、`api.js`、`sse.js` 和新增 `tests/testFileMention.py`；`server.py`、`chatView.js` 限相关附件/发送/错误处理函数。另核对 API 文档与旧 fileMention 计划。
- 发现问题：🔴 0 / 🟠 1 / 🟡 4 / 🔵 0。均为既有实现问题或能力差距，不是本轮新引入的问题。
- **核心结论：当前 @ 是“将本地文件内容拼成文本”，不是通用文件上传，也不是单纯传路径。** 没有压缩包解析器，也没有按扩展名设白名单；拒绝判据主要是 bytes 中是否包含 NUL。
- 本轮只增加隔离测试、计划和报告；**尚未修复/改变生产行为**。下一步需要用户选择“引用文件位置”还是“发送前解析内容”。

## 根因与链路

```text
@ 列表（所有文件 attachable:true）
→ chip 仅保存 {path,type}
→ POST /api/chat/stream
→ buildAttachmentMessage
→ readTextFile：整文件读取，含 NUL 则 RuntimeError
→ HTTP 400 {error:"二进制文件不支持：..."}
→ 前端透传错误
```

`server.py:571–574` 的附件检查早于 `agentManager.getAgent()`，所以**不是模型供应商拒收**；右侧预览通过 `/fileContent` 共用同一文本读取逻辑。

| 输入/条件 | 当前行为 | 证据 |
|---|---|---|
| UTF-8 文本，无扩展名、未知扩展名、甚至内容是文本的 `.zip` | 可内联 | 5 个参数化用例 |
| 标准库生成的真实 ZIP / TAR / TAR.GZ | 列表可选，发送与预览均 400 | 3 个纯函数 + 3 个 TestClient 用例 |
| 含 NUL 的二进制 / 含 NUL 的 UTF-16 文本 | 报“二进制文件不支持” | 2 个样本 |
| 无 NUL 的非法 UTF-8 bytes / 无 NUL 的 UTF-16 中文 / GB18030 中文 | 作为 UTF-8 替换解码后注入，内容失真 | 3 个样本；不声称所有非 UTF-8 都含替换字符 |
| 目录含文本+含 NUL 文件 | 保留文本，跳过后者并注明；全被跳过则报无可读文本 | 2 个用例 |

## 问题清单

### 🟠 High — 全量读取后才判断类型和预算，大压缩包可造成不必要内存压力

**位置：**`fileBrowser.py:37–48、147–159、197–199`。

**问题：**文件在判断含 NUL/超预算之前已 `read_bytes()` 全量进入内存。目录仅检查读取前的累计值，当前文件可令其越限，之后聚合层报错。引用大压缩包时，即便最终拒绝也已付出整包读取成本；并发请求可放大开销。测试确认预算越界顺序；未进行大文件内存压测，不声称已实测 OOM。

**修复方案：**在附件专用入口使用剩余预算的有界读取，不改成“删掉 NUL 检查”。例如：

```python
with target.open('rb') as source:
    raw = source.read(remainingBytes + 1)
if len(raw) > remainingBytes:
    raise RuntimeError('附件内容超过剩余预算。')
```

若用户选路径引用，超预算可转明确的“未内联”引用；目录应在追加当前文件之前按剩余预算处理，而不是生成超限结果再失败。预览与附件职责分开，避免顺手改变原有全量预览产品约定。

### 🟡 Medium — 前端允许选择所有文件，后端却只有文本内联能力

**位置：**`fileBrowser.py:46–48、66–69、191–194`；`fileMention.js openLevel/pickItem/getAttachments`；`server.py chatStream`。

**问题：**这是本次反馈的直接根因。压缩包既不被解压，也不作为路径引用兜底；用户能选中并不代表能发送。目录选中亦不代表目录中的二进制内容已被模型读取。

**修复方案：**先确认以下方向，不能替用户静默选择：

- **推荐最小方向：普通文本保持内联，不能安全内联的文件使用路径引用。** 仍用 `resolveInside()` 校验，提示“仅引用路径，内容尚未读取”，Agent 按已有工具权限自行检查。消息语义例如：
  ```text
  文件引用：data/input.zip
  内容状态：未读取、未解压；可通过工具按需检查。
  ```
- 若用户需要发送前内容解析，应按格式分别实现并限制条目数、解压字节、嵌套深度、路径穿越/链接和加密损坏包；不能给所有文件统一调用解压器。
- 不应只在前端置灰作为“支持压缩包”的修复，也不能改成将二进制替换解码或 base64 文本全部塞给模型。

### 🟡 Medium — NUL 判定不等于文本判定，非 UTF-8 文件可能静默失真

**位置：**`fileBrowser.py:46–48、154–159`。

**问题：**包含 ASCII 的 UTF-16 文本通常含 NUL，会被当二进制拒绝；某些 UTF-16 中文不含 NUL，却进入错误编码分支。GB18030 或无 NUL 二进制亦可能被 `errors='replace'` 转成失真文本。只看扩展名不能解决。

**修复方案：**附件内联必须采用明确支持的编码策略；UTF-8 严格解码失败时明确提示或转路径引用，而非静默替换。UTF-16 等支持需明确约定，可先识别 BOM，不引入未经要求的全编码自动猜测。

```python
content = raw.decode('utf-8')  # UnicodeDecodeError 必须由附件入口转明确提示/引用，不直接泄漏成 500。
```

严格 UTF-8 本身也不能识别所有无 BOM UTF-16（有的 bytes 同时是合法 UTF-8）；不能把它宣传为万能内容检测。

### 🟡 Medium — 文本里的合法附件结束标记导致正常源码无法引用

**位置：**`fileBrowser.py:195–196`。

**问题：**普通源码/文档只要含 `</attachment>` 字面量，就报“无法作为附件”。本项目 `fileBrowser.py` 本身也含该字面量，因此“其它文件”不仅可能因为二进制失败；该判断与内容是否可解码无关。

**修复方案：**若采用路径引用，可将此类不可安全内联内容也走显式引用兜底；若坚持内联，必须一并设计附件内容转义与回放解码（或结构化分离），不能仅删除冲突检查。不要为本次排查擅自改动历史消息协议。

### 🟡 Medium — 400 拒绝后不恢复输入/附件，气泡出现会误导用户

**位置：**`chatView.js:1073、1116–1118、1020–1039`。

**问题：**请求前已清空输入与 chip、追加用户气泡。普通 400 只显示错误、回到空闲态，不恢复草稿或撤回气泡。用户可能以为附件已发出，或者需要重新选择。`lastUserSend` 当前只用于特定 409 自动重试。

**修复方案：**后续若修复此体验，保存原始草稿、附件和本次乐观气泡节点，在确定“开流前拒绝”时标记失败并支持重试/恢复；仅在同一会话且没有用户新输入时自动恢复，防覆盖新草稿。涉及 `/skill` 时保留原始用户文本，不将注入后的 wireText 当草稿回填。不要对所有中断/500 盲目自动重发，以免重复执行已有副作用。

本项仅静态走查，未声称已有浏览器自动化/手动复现。

## 审核维度与保留设计

- Bug/资源/性能：已覆盖拒绝判据、失真解码、预算时机及全量读取。
- 模块融合/接口：区分列表、预览、发送、模型调用、历史文本协议；不能只改一个错误文案冒充支持。
- 并发：本轮不引入生产共享状态；候选草稿恢复需防旧请求覆盖新会话/新输入。
- 简洁/风格：新增测试小驼峰、规范文件头、pytest 临时 fixture；未添加解析依赖或一次性框架。
- 保留：workDir 拘禁、目录内越界链接跳过、目录 realpath 集合去环；错误在创建 Agent 前返回，避免无效模型请求。

## 修复优先级建议

1. **先由用户确认路径引用还是自动解析。** 推荐文本内联+其它文件路径引用，足以解决任意格式“提及”的最小需求，但不等于模型已经读取内容。
2. 实现选定方案时，必须使用有界读取及明确编码/状态，避免压缩包和大文件先全量读入。
3. 单独处理发送失败的草稿恢复与提示，测试会话切换、新输入和重试场景，不借本轮排查扩大改动。
