## 2. 实施方案

1. 新增小型显式恢复工具 `webApp/backend/sessionRecovery.py`：根据调用者给出的真实 workDir，使用现有 `workDirFolderName` 正向映射日志目录，禁止把 `-` 反向替换成 `/`。
2. 工具只读 JSONL/JSON 数组以及 SQLite（`mode=ro`，连接显式关闭），生成候选索引，不调用 agent/resume、不请求模型。
   - sessionId 来自文件名；首条用户消息前 20 字作恢复标题。
   - workDir 来自明确参数；providerId/modelId/lastUsage 来自 usage.db 最后记录，不从响应 model 名猜测。
   - createdAt/updatedAt 分别取日志文件事件顺序中首个/最后一个字符串时间戳，不取时间极值；累计 usage/contextTokens 按现有 conversation 口径读取 assistant usage。
   - 最后记账记录明确按唯一持久主键 `id` 的插入序选取（`ORDER BY id` 后按 sessionId 保留最后一条），对齐现有 `usageStore.queryLastUsageTurn` 的 `ORDER BY id DESC LIMIT 1`，不依赖 SQLite 天然行序或响应模型别名。
   - 无法确认的元数据、重复 sessionId、无法解析日志明确报错，不能静默丢弃或使用当前默认模型。
   - 输出明确标记为恢复索引（不声称原自定义标题、仅建未发送的空会话、未发请求的切模型能原样恢复）。
3. `jsonlLog.readEvents` 增加合法 JSON 事件数组及其后续追加 JSONL 的读取兼容，保持原 JSONL 中崩溃末行跳过行为，过滤非对象行；不转换、不覆写现存正文。恢复工具另用严格 `readRecoveryEvents`：坏数组、非对象元素、任何坏 JSONL 行（含截断末行）均报错，不调用具有 mkdir 行为的 logger 构造器，不静默丢事件。
4. 先做临时目录回归：仅有旧日志/usage.db，没有索引 → 生成候选索引 → 实际 `listSessions/loadMessages` 返回非空；覆盖两种日志格式、元数据恢复、只读 DB、失败不输出，以及完整测试。
5. 默认模型新窗口 `pi -p` 审核方案；按反馈修订。

## 3. 现场恢复保护

- 写入前在 `~/.flamingo/backups/` 创建独立恢复备份，复制所有 JSONL；SQLite 使用只读源连接的 backup API 创建一致副本。
- 确认新旧索引仍不存在；若已存在，停止应用，不覆盖/合并用户新数据。
- 使用备份快照生成候选，校验候选与源文件一一对应、所有历史均能解析；实际 index 写入使用同文件系统的原子无覆盖发布（hard link），目标已存在则失败。
- 不停止或重启 Web 进程。现有进程每次读索引，无缓存，索引发布后列表应可直接显示；JSON 数组兼容需服务重启后生效。
- 验证前后现存正文及 usage.db 的 SHA-256；若后台仍有写入，停止应用并重新协调，不能宣称恢复期间无变化。
- 审核补充：仅哈希 usage.db 不能覆盖 WAL 提交。应比对只读数据库完整逻辑快照（按主键排序）及同连接 `PRAGMA data_version` 稳定性，检查 journal_mode 和 WAL 情况；不把主文件哈希当作 WAL 场景的完整证明。
- 不新建任何原工作目录。临时测试目录已不存在的日志仍可看历史，续聊需先由用户处理目录；不以默认工作目录冒充。
