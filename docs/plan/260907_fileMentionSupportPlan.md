# @ 文件支持范围排查与修复决策计划

## 1. 目标与本轮边界

用户反馈：使用 `@` 引用压缩包或其它文件时提示不支持。

本轮完成：确认真实调用链、用样本复现、说明当前支持边界、提出最小修复方向并请用户确认。用户尚未说明希望“让 Agent 知道路径并自行处理”还是“发送前自动解析/解压内容”，两者不是同一个需求；**不默认为自动解压，也不擅自改成路径引用**。

成功标准：
- 定位“不支持”发生在前端、Web 后端还是模型供应商，并用自动化断言证明。
- 覆盖可读文本、压缩包、其它含 NUL 文件、非 UTF-8 文本、目录，以及独立的大小/数量/标记限制。
- 说明前端可选择与后端可发送的差异；明确“被拒”与“错误地被当作文本发送”两类情况。
- 新子代理审核计划，修复后重审，直至无明显问题；最终报告与测试结果落档。
- 不更改生产代码、模型配置、用户会话/历史、现有未提交修改；测试不进行真实模型请求（计划独立审核所需子代理调用除外）。

## 2. 已确认的调用链（后端经专项测试，前端静态走查）

1. `fileMention.js openLevel()` → `api.listFiles()` → `GET /api/sessions/{id}/files` → `fileBrowser.listDir()`：所有文件均返回 `attachable: true`，不按扩展名或内容过滤。
2. 选择后生成 `{path, type}` chip；前端不预读内容，`chatView.send()` 将其放入 `/api/chat/stream` 请求。
3. `server.chatStream()` 在创建 Agent/开启流之前调用 `buildAttachmentMessage()`。
4. 文件一律走 `readTextFile()`：校验工作目录边界和常规文件 → 全量 `read_bytes()` → 含 `b'\x00'` 抛出 `RuntimeError('二进制文件不支持：...')` → 否则以 UTF-8 `errors='replace'` 解码。
5. 后端统一将 RuntimeError 映射为 HTTP 400；SSE 客户端透传 `error` 字段。并非模型先接收到压缩包再拒绝。
6. 目录引用递归拼接文本、跳过含 NUL/不可读文件；全为这类文件时失败。目录最多展开 100 个文件；字节检查在读取下一个文件前，当前文件可能使累计超过 1 MiB，之后聚合层整请求拒绝，并非始终安全截断至预算内。
7. 现有合计 1 MiB / 8 个附件、`</attachment>` 内容冲突校验仍会独立导致失败。1 MiB 按原始文件字节累计，不是最终消息长度，也不是读取内存上限。
8. 右侧文件预览同样调用 `readTextFile()`，但不走附件聚合的数量/合计大小/标记冲突检查。
9. 前端发送前已清空输入和附件 chip、追加用户气泡；普通 400 后显示错误但不恢复草稿或撤销气泡。气泡出现不代表后端已成功接收；本轮只静态记录，不引入浏览器测试框架。

## 3. 排查与验证方案

### 步骤 A：只读走查 → 验证：逐段调用关系和错误文本

读取 `fileMention.js`、`fileBrowser.py`、`fileExplorer.js`、`api.js`、`sse.js` 及 server/chatView 中的相关函数；对照 API 文档与既有 fileMention 计划。无关未提交修改仅记录，不清理、不回退。

### 步骤 B：新增隔离 characterization tests → 验证：`uv run pytest -q tests/testFileMention.py`

新增 `tests/testFileMention.py`（小驼峰命名、文件头 Author/Version/Date/Description）。这是**当前行为刻画测试，不是修复后的验收用例**；通过代表复现已确认，绝不代表压缩包已支持。

使用 pytest 的 `tmp_path`（以 fixture 别名实现新增变量小驼峰）、`monkeypatch` 与标准库在临时目录内生成样本；不读取用户提供之外的真实压缩包、不解压至工作目录。

测试范围：
- UTF-8 中文文本、无扩展名、未知扩展名文本均可拼接，说明没有扩展名白名单。
- 用标准库生成真实 ZIP、TAR、TAR.GZ 样本，验证样本含 NUL 后被拒绝；不将合成头部冒充完整 RAR/7z/PDF 文件，也不声称所有二进制都一定含 NUL。
- 含 NUL 的普通二进制和 UTF-16 样本被拒；UTF-16 不含 NUL 的样本及其它无 NUL 的非法 UTF-8 bytes 进入 UTF-8 替换解码分支，暴露“非 UTF-8/非文本也可能误入”的边界，不能按编码名称笼统分类。
- 目录含文本+二进制：只注入文本且注明跳过；仅二进制目录失败。101 个小文本文件在 100 个处截断并注明；目录单文件/累计字节跨越 1 MiB 时，刻画展开层越限、聚合层拒绝的现状。
- 单次 >8 个、文本合计 >1 MiB、内容含 `</attachment>` 分别触发独立异常。
- 直接引用越界路径或越界符号链接：拒绝。合法目录包含正常文本及越界链接：跳过外部链接，保留正常文本且外部内容不被注入。外部目标放在 pytest 临时目录内、测试 workDir 外；不放松路径校验。
- FastAPI TestClient 使用伪会话、伪 Web token；mock `getAgent` 为失败哨兵，证明压缩包发送返回 400 且尚未调用 Agent。GET files 返回 `attachable: true`、GET fileContent 返回同一拒绝消息。
- 全程 mock 会话查询，不写 sessions.json / jsonl，不调用模型或新建真实会话。

## 4. 候选修复方向（待用户确认，不在本轮实现）

### A. 路径引用兜底（推荐的最小方向）

- 保持普通文本内联的兼容行为；对无法安全内联的文件发送经过 workDir 边界校验的路径/基础元数据，而不是原始二进制或整包内容。
- 在模型消息和界面明确“仅路径引用，内容尚未读取”；Agent 可视工具权限和环境能力按需调用工具检查，不承诺每种格式都能解析。
- 与文本预览分开：能 `@` 引用不等于能在预览弹层显示内容；不直接放松 `readTextFile()` 的文本安全边界。
- 后续实施前需细化：有界读取与文本判定、超大文本是否也引用路径、引用信息的字节预算、路径转义、历史回放和错误路径回归。
- 优点：覆盖任意格式的“提及”需求，少依赖、不自动解压、不把二进制乱码塞给模型。
- 代价：模型仅知道文件位置，没有直接得到文件内容；读取/解包依赖工具与用户授权。

### B. 发送前解析内容

- 明确支持格式后分别处理，如 ZIP/TAR 提取清单与选定文本；PDF/Office/图片不是同一类解析能力，不能用解包器统包。
- 必須为压缩炸弹、条目数、单项/总解压字节、目录穿越、符号链接、嵌套包、加密/损坏包制定限制；不直接 `extractall()`。
- 优点：模型能直接得到部分解析内容。
- 代价：功能范围、依赖和安全边界明显更大；格式需用户确认，不适合作为本次排查时的默认实现。

不推荐：删除 NUL 校验直接替换解码、只修改扩展名白名单、把全部文件简单 base64 当文本注入、无上限自动解压。
